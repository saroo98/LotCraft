## Method and completion criteria

Each confirmed defect needs a causal source trace, a reproducer where feasible, a minimal fix, and fresh verification. Hypotheses and runtime-only checks remain explicitly separate. Existing Python source-string checks and independent reference models are not proof that the MQL runtime executes correctly.

Completion means all confirmed in-scope findings are resolved locally or have a precise external dependency, all requested subsystems have an audit disposition, available safe tests/builds have run, and the final diff and production immutability checks have been reviewed. It does not mean the project has zero bugs.

## Baseline

- Runtime: MQL5 EA and 11 local headers, custom canvas/editor, Win32 integration.
- Installer/updater/signing: Go module `lotcraft.local/installer`, Go 1.23 minimum, Windows-specific setup; public Ed25519 key is tracked.

- Isolated runtime: Hyper-V inventory permission denied. No isolated runtime is established and no terminal is launched.
- Baseline test results: 236 Python cases passed. See [verification](AUDIT_VERIFICATION_2026-09-09.md) for proof boundaries.

MQL source names below resolve under `MQL5/Experts/LotCraft/`. Installer names resolve under `installer/`; script paths are repository-relative.

## External dependencies and unverified behavior

- **Native acceptance:** Hyper-V inventory fails with insufficient permissions. No configured isolated MT5 runtime is established. The exact remaining scenarios are listed in the verification report. No live terminal was launched or controlled.
- **Public privacy repair:** Existing remote verification-asset cleanup requires explicit remote-write permission. No account number or terminal ID was observed in that checked asset; the confirmed disclosure is absolute workspace paths. The local producer is repaired, but the public bytes are unchanged.
- **Security detection:** Windows Security initially blocked a race-instrumented setup test executable. After the user reported allowing the detected item, the full race suite passed. The assistant changed no protection settings. A passing rerun does not determine whether the detection was correct or a false positive. Independent artifact/security review remains separate from test correctness.
- **No deployment:** These fixes are not installed, signed, committed or published. The audit EX5 differs from the old installed EX5 by design. Both production installations and the separate dirty main checkout are preserved. Existing published 1.2.0 assets retain their previous code.
- **Scheduling/product boundary:** The updater launches once per EA initialization after ten seconds. Attempts, including failures, are throttled for 24 hours. A continuously attached EA has no recurring daily launch, so notification within 24 hours is not guaranteed. Adding a scheduler needs a separate product decision.
- **Crash boundary:** Four-file replacement supports rollback for detected failures, not power-loss/process-crash atomicity. Terminal-global persistence is also not a multi-key transaction. A recovery journal is separate architectural work; detected rollback failure now retains backups and reports the failure accurately.
- **Native installation boundary:** Actual signed upgrade, popup, activation on reattachment, and a signed upgrade through a real approved junction remain unverified. Synthetic Windows file/mutex/ACL tests do not substitute for that acceptance.
- **Product boundaries:** The native risk-only MessageBox cannot style its lines separately. Minimum chart dimensions, missing visible commission editor, and historical 1.0.0 README images are documented. Custom confirmation, new inputs or overflow navigation need approval, not speculative redesign during this audit.
- **Residual hypotheses:** Same-count ticket churn is not a transactional inventory snapshot. Extreme malformed finite broker values could overflow aggregate arithmetic; no realistic broker reproducer was established. Neither is silently represented as a fixed defect.
